# CMake reads the schema directory at build time

## The decision

The C++ pack's copy of the shipped schemas is generated on every build whose
inputs have changed, by a CMake script reading `schemas/`, and no copy is
committed.

    cpp/cmake/generate-shipped.cmake   reads the directory, writes a header
    build/generated/wrench/shipped.hpp the bytes, as string literals

Two mechanisms, because they catch different changes. `file(GLOB ...
CONFIGURE_DEPENDS)` re-reads the directory listing on every build, so a schema
added or removed reaches the pack. The generator runs as a custom command with the
schema files as `DEPENDS`, so a schema edited reaches it too.

This is `build.rs` in another language, and it has the same consequence: there is
no `shipped-schemas-are-current` task for C++, because there is no committed copy
to go stale.

## Why not the shape Go and Python use

Both run `bin/generate-shipped.py` into a committed file, which is a second copy of
every schema, held honest by a gate task comparing bytes. FR-3.2 exists to prevent
exactly that drift, and the task is what makes the cost acceptable there.

C++ needs no such trade. CMake reads a directory, so the copy can be made during
the build and never committed, and a stale one cannot exist.

## Why not `configure_file`

infobot's C++ carries one `configure_file` per named schema, which is the shape
FR-3.7 forbids: the list of filenames lives in the build file, so adding a schema
means editing a second place. The glob has no list in it.

## Why the bytes are escaped rather than wrapped in a raw literal

A raw string literal needs a delimiter that does not appear in the content, which
is a property of the content nobody would be checking. The generator escapes
backslashes and quotes and writes one literal per line of the file, so the header
is diffable and no schema can break it by holding a particular sequence.

## What the pack does with the generated set

`wrench::shipped::documents` is a `constexpr` array of the file name and the bytes.
The pack's own code turns that into the shipped set: each document is decoded
through the pack's JSON codec, the `$id` it declares is read from the document
itself, and `wrench::schemas::all()` reports the three together.

The `$id` is deliberately not generated beside the bytes. FR-3.6 names a schema by
the `$id` it declares, so reading it from the document keeps one authority; a
generated copy of it would be a second place for the same string to be wrong.

`schemas::by_stem` is the whole of the discovery path, and it is public. A schema
added to `schemas/` is reachable through it on the next build with nothing in the
pack edited. The four named accessors, `envelope`, `jig`, `manifest` and
`definitions`, are names for members of that set, and the suite asserts the set has
four members so a fifth arriving fails a case that says it needs an accessor and a
fixture of its own.

## Two things the generated header is not

**It is not checked by the gate's analysis tasks, and that is deliberate.** The
generated directory is a system include directory, so clang-tidy, cppcheck and
include-what-you-use treat it as they treat the fetched libraries. Nothing in it is
written by hand, and a formatter's opinion of generated data is noise.

**It is not on the pack's installed interface yet.** It is included by
`src/schema.cpp` alone and no public header names it, so a consumer compiles
against `include/wrench` and the generated bytes stay inside the library. Whether
an installed package carries it is the export task's question and not this one's.
